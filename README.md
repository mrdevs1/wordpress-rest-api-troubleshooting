## Overview

The WordPress REST API allows WordPress sites to exchange structured data using HTTP requests and JSON responses. It is used by the block editor, plugins, themes, external applications, and custom integrations.

The default REST API index is generally available at:

```text
https://example.com/wp-json/
```

Replace `example.com` with your own domain before testing.

Official documentation: https://developer.wordpress.org/rest-api/

## Common Symptoms

| Symptom                            | Possible cause                                           |
| ---------------------------------- | -------------------------------------------------------- |
| REST API returns 404               | Rewrite rules, incorrect route, or missing endpoint      |
| Invalid JSON response              | PHP warnings, fatal errors, or unexpected output         |
| HTTP 401 Unauthorized              | Missing or invalid authentication                        |
| HTTP 403 Forbidden                 | Permissions, security rules, or access restrictions      |
| HTTP 500 Internal Server Error     | PHP exception, fatal error, or server configuration      |
| REST API request times out         | Slow PHP execution, database queries, or resource limits |
| Custom endpoint is missing         | Route registration or plugin loading problem             |
| Authentication headers are missing | Web server or proxy configuration                        |

These are possible causes, not definitive diagnoses. Inspect the actual response and logs before changing the configuration.

## 1. Test the REST API

### Step 1: Open the API index

Visit:

```text
https://example.com/wp-json/
```

A working endpoint generally returns JSON describing the available API routes.

### Step 2: Test a public posts endpoint

```text
https://example.com/wp-json/wp/v2/posts
```

If the site contains publicly accessible posts, this endpoint should normally return a JSON response.

### Step 3: Test using cURL

```bash
curl -i https://example.com/wp-json/
```

To inspect only the HTTP response headers:

```bash
curl -sS -D - -o /dev/null https://example.com/wp-json/
```

Review the HTTP status code and response headers. A successful response does not necessarily mean every endpoint or authentication method is working correctly.

## 2. Fix REST API 404 Errors

A 404 response can indicate that the requested route is unavailable or that the web server is not routing the request correctly.

### Troubleshooting steps

1. Confirm the URL and route are correct.
2. Open **WordPress Admin → Settings → Permalinks**.
3. If appropriate, click **Save Changes** to refresh rewrite rules without changing your preferred permalink structure.
4. Test `/wp-json/` again.
5. Check whether the affected endpoint is registered by WordPress or its responsible plugin.
6. Review web server rewrite configuration and security rules if the issue persists.

For sites without pretty permalinks, test the alternative route format:

```text
https://example.com/?rest_route=/
```

For the posts endpoint:

```text
https://example.com/?rest_route=/wp/v2/posts
```

Do not replace production rewrite rules with generic configuration snippets without checking your current server setup.

## 3. Fix Invalid JSON Responses

The message “The response is not a valid JSON response” may occur when WordPress expects JSON but receives PHP errors, HTML, or other unexpected output.

### Troubleshooting steps

1. Reproduce the problem and inspect the browser's Network panel.
2. Identify the failed REST API request.
3. Review its HTTP status, response headers, and response body.
4. Check the PHP error log and WordPress debug log.
5. Look for PHP warnings, fatal errors, unexpected whitespace, or output generated by plugins and themes.
6. Check whether a security service, proxy, or cache is returning an HTML error page.
7. Test again after addressing the confirmed cause.

### Enable temporary WordPress debugging

Back up `wp-config.php` before editing it. If appropriate, configure debugging in a controlled environment or during a maintenance window.

Add or update these constants before the line that says `/* That's all, stop editing! Happy publishing. */`:

```php
define( 'WP_DEBUG', true );
define( 'WP_DEBUG_LOG', true );
define( 'WP_DEBUG_DISPLAY', false );
```

If these constants already exist, edit their existing definitions instead of declaring them a second time.

Review:

```text
wp-content/debug.log
```

**Important:** The log can contain sensitive information. Restrict access to it and remove or disable temporary debugging after the investigation. Do not leave public-facing debug output enabled on a production website.

## 4. Troubleshoot 401 and 403 Errors

### HTTP 401 — Unauthorized

Possible causes:

* Authentication credentials are missing or incorrect.
* An application password is invalid or revoked.
* Cookie authentication is missing a valid REST API nonce.
* Authorization headers are not reaching PHP.

For external integrations, WordPress Application Passwords can be used over HTTPS when supported by the site and integration.

Example read-only request:

```bash
curl --user 'USERNAME:APPLICATION_PASSWORD' \
  'https://example.com/wp-json/wp/v2/posts'
```

Replace the placeholders with your own credentials. Never publish real credentials in a repository, screenshot, command history, or support ticket.

### HTTP 403 — Forbidden

Possible causes:

* The authenticated user lacks the required capability.
* A plugin or web application firewall blocks the request.
* Server-level access rules deny the request.
* A custom endpoint has a restrictive permission callback.

Check the error response and security logs to determine which layer is rejecting the request.

Do not disable authentication or security protections as a permanent workaround.

### Check authorization headers

In some PHP CGI/FastCGI configurations, the web server may not forward the `Authorization` header as expected.

Review the relevant server configuration and the official WordPress REST API FAQ before making changes.

Reference: https://developer.wordpress.org/rest-api/frequently-asked-questions/

## 5. Diagnose Plugin and Theme Conflicts

A plugin or theme can interfere with REST API requests by changing authentication, modifying responses, producing unexpected output, or blocking routes.

### Recommended process

1. Back up the site and database.
2. Reproduce the issue on staging whenever possible.
3. Record the affected route and exact response.
4. Check recent plugin, theme, and configuration changes.
5. Deactivate suspected extensions one at a time in staging.
6. Switch to a standard WordPress theme temporarily if appropriate.
7. Retest after each change.
8. Restore the original configuration and document the result.

If the issue disappears after a particular change, repeat the test to confirm the cause before applying a production fix.

Avoid disabling all security plugins on a live site without a controlled testing plan.

## 6. Check Server and Security Configuration

If the REST API works on some routes but fails on others, inspect the relevant server and security layers.

### Apache and LiteSpeed

* Review `.htaccess` rewrite rules.
* Check the web server error log.
* Look for ModSecurity or web application firewall events.
* Confirm that WordPress requests are reaching the correct document root.

### Nginx

* Review the site's `location` and `try_files` directives.
* Confirm that requests reach the intended WordPress front controller.
* Inspect PHP-FPM and Nginx logs for errors.

### Cloudflare or another proxy

* Review firewall events for the affected URL.
* Check whether bot protection or custom rules challenge API requests.
* Inspect caching rules and response headers.
* Confirm that the origin server is returning the expected response.

Change only the rule responsible for the failure. Avoid broad firewall exclusions or globally disabling protections.

## 7. Troubleshoot Custom Endpoints

Custom REST API routes must be registered correctly and include an appropriate permission callback.

Example read-only endpoint for a custom plugin:

```php
<?php
/**
 * Register a simple public REST API endpoint.
 */

add_action( 'rest_api_init', function () {
    register_rest_route(
        'example-plugin/v1',
        '/status',
        array(
            'methods'             => 'GET',
            'callback'            => function () {
                return array(
                    'status' => 'ok',
                );
            },
            'permission_callback' => '__return_true',
        )
    );
} );
```

After placing this code in a suitable custom plugin, test:

```text
https://example.com/wp-json/example-plugin/v1/status
```

Expected JSON:

```json
{
  "status": "ok"
}
```

This example is intentionally public and returns no private data. Do not use a public permission callback for endpoints that expose private information or perform privileged actions.

### Custom endpoint checklist

* Register routes on `rest_api_init`.
* Use a unique namespace and route.
* Select the correct HTTP method.
* Provide a permission callback appropriate to the data and operation.
* Validate and sanitize incoming parameters.
* Use WordPress response helpers where appropriate.
* Return structured data rather than printing JSON directly.
* Check PHP logs if the endpoint returns an error.

Reference: https://developer.wordpress.org/rest-api/extending-the-rest-api/routes-and-endpoints/

## 8. Use Safe Diagnostic Commands

### Check the HTTP response

```bash
curl -i https://example.com/wp-json/
```

### Check a public posts endpoint

```bash
curl -sS -i \
  'https://example.com/wp-json/wp/v2/posts?per_page=1'
```

### Inspect the response without printing the full body

```bash
curl -sS -o /dev/null \
  -w 'HTTP status: %{http_code}\nContent type: %{content_type}\n' \
  https://example.com/wp-json/
```

### Using WP-CLI

If WP-CLI is installed and you have authorized access to the correct WordPress installation, inspect the environment:

```bash
wp core version
wp plugin list
wp theme list
```

Run these commands from the correct WordPress directory or specify the installation path with `--path=/path/to/wordpress`.

These commands inspect the installation; they do not directly repair REST API failures.

## Troubleshooting Checklist

Use this checklist before closing an issue:

* [ ] Confirm the exact failing REST API URL.
* [ ] Record the HTTP status and response body.
* [ ] Test the API index at `/wp-json/`.
* [ ] Verify the route and HTTP method.
* [ ] Refresh permalink rules if appropriate.
* [ ] Check PHP, WordPress, and web server logs.
* [ ] Verify authentication and user capabilities.
* [ ] Inspect security and proxy events.
* [ ] Test plugin and theme conflicts on staging.
* [ ] Confirm any custom endpoint's registration and permissions.
* [ ] Retest after applying the fix.
* [ ] Remove temporary debugging and protect diagnostic logs.

## Security Best Practices

* Always use HTTPS for authenticated API requests.
* Never commit passwords, application passwords, API tokens, or private customer data.
* Use least-privilege accounts for integrations.
* Validate and sanitize incoming data.
* Enforce authorization checks for private data and write operations.
* Avoid exposing PHP errors to visitors.
* Keep WordPress, plugins, themes, and PHP updated.
* Back up the site before production configuration changes.
* Do not disable the REST API globally to solve an isolated endpoint problem.
